# 多賣家電商平台 需求規格

> 狀態：定版
> 版本：1.8
> 最後更新：2026-10-15

## 1. 專案目的

以多賣家電商平台（類似 Amazon Marketplace）為題，實作並驗證高流量、分散式系統與雲端架構的能力。後端使用 Java / Spring。前端排在後端主要功能完成之後開發，現階段不實作，但後端的介面設計要以日後供前端使用為前提。

專案以壓測驅動演進：先訂目標，壓測找出瓶頸，再調整架構並記錄決策。

## 2. 角色

| 角色 | 說明 |
|---|---|
| 訪客 | 未登入的使用者，只能瀏覽與搜尋商品 |
| 會員 | 已註冊並登入的買家，可使用購物車、結帳、付款、使用折價券、參加搶購、查訂單、申請退款 |
| 外部賣家 | 上架商品、管理庫存、出貨、審核退款、報名搶購活動、看自己的銷售報表與結算對帳單 |
| 平台自營賣家 | 與外部賣家相同的銷售流程，但不抽成、不撥款 |
| 平台營運 | 開設搶購檔期、審核賣家報名、發放折價券、設定抽成比例、裁決退款申訴、處理對帳差異、看跨賣家報表 |
| 排程系統 | 執行批次任務 |
| 外部金流 | 獨立的模擬服務，處理付款、退款與撥款 |

會員、賣家、平台營運是三種獨立的帳號類型，互不通用。

## 3. 功能需求

| 訂單 | 結帳、拆單、狀態流轉、取消 | 深 |
| 庫存 | 入庫與調整、預扣、確認、釋放，不可超賣；每次變動留下異動紀錄 | 深 |
| 付款 | 一次付款對多張子訂單、失敗重試、冪等 | 深 |
| 退款 | 以子訂單為單位申請、核准、退款、庫存回補 | 深 |
| 帳本 | 所有金流事件以複式記帳記錄，可由分錄重建各項餘額 | 深 |
| 限時搶購（搶購本身） | 立即購買、限量、每人限購、搶購庫存與一般庫存互不超賣 | 深 |
| 限時搶購（檔期管理） | 平台開檔期、賣家報名、平台審核 | 淺 |
| 折價券 | 平台發券、結帳鎖定、付款核銷、取消歸還、折扣分攤到子訂單 | 深 |
| 批次 | 高頻任務（逾時取消、付款結果查詢、搶購檔期切換）與每日任務（子訂單狀態推進、對帳、結算、撥款、報表、庫存核對、券到期），見 3.5 | 深 |
| 商品與搜尋 | 上架與下架、分類、關鍵字搜尋、商品頁 | 中 |
| 查詢 | 各角色的列表、搜尋、詳情與報表查詢，見 3.11 | 中 |
| 購物車 | 增刪改、跨賣家，僅限會員 | 中 |
| 資料隔離 | 賣家只能存取自己的商品、訂單、報表與結算 | 中 |
| 稽核與異動追蹤 | 所有資料異動可追查操作者、時間與變更內容，依重要程度分三級 | 中 |
| 規則告知 | 條款版本與同意紀錄、操作時的規則提醒，見 3.12 | 淺 |
| 會員 | 買家註冊、登入、維護收件資訊 | 淺 |

| 認證與權限 | 帳號密碼登入、失敗鎖定、賣家與營運帳號的角色權限，見 3.13 | 中 |
| 物流 | 賣家標記出貨、會員確認收貨，只做狀態變更 | 淺 |
| 通知 | 訂單事件觸發，只記錄不實際發送 | 淺 |

### 3.1 拆單模型與訂單狀態

一次結帳產生一張結帳單與多張子訂單，每張子訂單對應一個賣家。一張結帳單最多只有一筆成功的付款。各賣家可分別出貨，子訂單可分別退款。

結帳的規則：

- 結帳時預扣庫存，付款成功後才確認扣除
- 任一商品庫存不足或已下架，整筆結帳失敗
- 結帳以當下的商品價格為準，子訂單保存商品名稱、單價與數量的快照，之後商品改價或改名不影響既有訂單
- 結帳時須選擇一筆收件資訊（收件人、電話、地址），同一張結帳單的所有子訂單使用同一筆；子訂單保存收件資訊的快照，之後會員修改收件資訊不影響既有訂單
- 單一商品每次結帳最多 99 件
- 每位會員同時最多只能有一張一般的「待付款」結帳單，以及一張搶購的「待付款」結帳單，避免惡意佔住庫存；要再結帳須先付款或取消既有的結帳單

結帳單的狀態：

| 狀態 | 進入條件 |
|---|---|
| 待付款 | 結帳成功 |
| 已付款 | 付款成功 |
| 已取消 | 逾時未付款，或會員主動取消 |

取消的規則：

- 結帳單建立後 30 分鐘內未付款成功即逾時取消（搶購為 10 分鐘，見 3.4）
- 會員可主動取消「待付款」的結帳單
- 付款失敗不會取消結帳單，會員可在時限內重新付款
- 超過時限後即不可再發起付款，即使逾時取消任務尚未執行到這張結帳單
- 有付款正在處理中或已經成功的結帳單不可取消，待付款結果確定後再處理。付款成功後到結帳單更新為「已付款」之間可能有數秒延遲，取消前必須確認付款的實際狀態
- 結帳單取消時，其所有子訂單一併取消，釋放預扣的庫存並歸還折價券
- 會員主動取消一般結帳單時，該結帳單的商品放回購物車；逾時取消與搶購結帳單的取消不放回
- 放回時購物車已有同一項商品，數量直接合併，即使合併後超過 99 件；超過 99 件的商品在結帳時被擋下，會員須先減少數量。系統不自行調整數量，由會員決定

子訂單的狀態：

| 狀態 | 進入條件 |
|---|---|
| 待付款 | 結帳成功 |
| 已付款 | 付款成功 |
| 已出貨 | 賣家標記出貨 |
| 已簽收 | 會員確認收貨，或出貨滿 7 天仍未確認時自動簽收 |
| 已完成 | 簽收滿 7 天，且沒有尚未結束的退款申請或申訴（見 3.8） |
| 退款申請中 | 會員申請退款或提出申訴，退款事項尚未結束（含審核中、申訴中、核准後等待退款完成） |
| 已退款 | 退款成功 |
| 已取消 | 結帳單被取消 |

完成與結算的規則：

- 子訂單在付款後、完成前都可以申請退款，流程見 3.8
- 子訂單完成後不可再退款
- 只有已完成的子訂單會進入賣家結算，因此不會發生已撥款後又要向賣家追回款項的情況

### 3.2 賣家模型

賣家是一個組織，與使用者帳號是不同的概念。一個賣家底下可以有多個帳號。賣家與其帳號由平台營運建立，不提供賣家自行註冊。

賣家分為兩種類型，銷售流程（上架、結帳、拆單、庫存、出貨、退款）完全共用，差異只在金流：

| 項目 | 平台自營賣家 | 外部賣家 |
|---|---|---|
| 平台抽成 | 無 | 有 |
| 結算撥款 | 不需要，收入直接歸平台 | 每日結算後撥款 |
| 帳本記法 | 子訂單完成時記為平台營收 | 子訂單完成時記為應付賣家款項 |

抽成的規則見 3.10。

平台自營部門的員工使用賣家帳號操作自營賣家，與營運帳號分開，避免自營部門審核自己的搶購報名或裁決自營商品的退款申訴。同一個人若兩種工作都要做，分別使用兩個帳號。

子訂單建立時保存賣家類型的快照，之後賣家資料變動不影響該子訂單的抽成與帳本記法。

### 3.3 庫存模型

平台自營賣家與外部賣家用相同的方式管理庫存。

- 每個商品只有一組一般庫存數字，不分倉庫
- 賣家透過「入庫」或「調整庫存」設定數量，只記錄數量與原因，不記錄貨品來源

每個商品的一般庫存維護兩個數字：

| 數字 | 意義 |
|---|---|
| 可賣數量 | 目前還能被下單的數量 |
| 預扣數量 | 已被結帳單保留、尚未付款的數量 |

庫存數字在每次異動發生時立即更新，並同時新增一筆異動紀錄，兩者在同一個資料庫交易內完成。系統不提供「只改數字、不留紀錄」的途徑。

| 異動類型 | 發生時機 | 可賣數量 | 預扣數量 |
|---|---|---|---|
| 入庫 | 賣家增加庫存 | 增加 | 不變 |
| 調整 | 賣家修正數量（例如盤點差異、商品毀損） | 增加或減少 | 不變 |
| 預扣 | 會員結帳 | 減少 | 增加 |
| 確認 | 付款成功 | 不變 | 減少 |
| 釋放 | 結帳單取消 | 增加 | 減少 |
| 退款回補 | 退款後商品回到可賣狀態，見 3.8 | 增加 | 不變 |
| 搶購劃撥 | 搶購報名審核通過 | 減少 | 不變 |
| 搶購歸還 | 搶購檔期結束 | 增加 | 不變 |

任何時候可賣數量與預扣數量都不得小於零。

參加搶購的商品另有一組搶購庫存，同樣維護可賣數量與預扣數量。搶購劃撥時，數量從一般庫存的可賣數量移到搶購庫存的可賣數量；搶購歸還時反向移回。搶購庫存的預扣、確認、釋放與一般庫存規則相同，也同樣留下異動紀錄。

退款回補一律回到一般庫存，即使該子訂單當初是以搶購購買。

### 3.4 限時搶購

檔期管理：

1. 平台營運開設搶購檔期，設定起訖時間
2. 賣家（含平台自營）在檔期開始前拿自己的商品報名，提出活動價、釋出數量與每人限購數量
3. 活動價必須低於報名當時的商品原價，釋出數量不得超過該商品當下的一般可賣數量
4. 同一商品在同一段時間內只能參加一個檔期
5. 平台營運須在檔期開始前審核。審核通過時進行搶購劃撥；若此時一般可賣數量已不足，審核失敗。檔期開始時仍未審核的報名自動拒絕
6. 檔期開始後，商品才能以活動價購買
7. 檔期結束時，搶購庫存的可賣數量全部歸還一般庫存
8. 檔期結束前建立的搶購結帳單仍可在其 10 分鐘時限內付款；若之後被取消，釋放出來的數量同樣歸還一般庫存

購買流程：

- 搶購採「立即購買」，不經過購物車
- 一張搶購結帳單只包含一項搶購商品，數量可以多件
- 同一會員在同一檔期對同一商品，待付款與已付款的數量合計不得超過每人限購數量
- 結帳單取消後，該數量的限購額度退還；付款後退款則不退還額度
- 搶購結帳單建立後 10 分鐘內未付款成功即逾時取消
- 搶購結帳單不能使用折價券
- 搶購庫存售完或檔期結束後即不可再以活動價購買
- 檔期內同一商品仍可透過購物車以原價從一般庫存購買
- 付款之後的出貨、退款、完成、結算流程與一般子訂單相同

### 3.5 批次任務

批次任務依執行頻率分為兩類。高頻任務每隔數分鐘以內執行一次，處理有時效性的狀態推進；每日任務在離峰時段執行，處理大量資料的核對與結算。

高頻任務：

| 任務 | 說明 |
|---|---|
| 逾時取消 | 結帳單逾時未付款時自動取消，釋放庫存並歸還折價券 |
| 付款結果查詢 | 對狀態為「處理中」的付款、退款與撥款，主動向金流查詢結果並推進狀態；超過 1 小時仍無法確認時發出告警，由平台營運處理 |
| 搶購檔期切換 | 檔期開始時開放活動價與搶購庫存，並自動拒絕仍未審核的報名；檔期結束後將搶購庫存的可賣數量歸還一般庫存，直到該檔期沒有剩餘的搶購庫存為止 |

每日任務：

| 任務 | 說明 |
|---|---|
| 子訂單狀態推進 | 已出貨滿 7 天仍未確認收貨的子訂單自動簽收；已簽收滿 7 天且沒有尚未結束的退款申請或申訴的子訂單標記為「已完成」，並記入帳本；賣家 3 天未處理的退款申請自動核准 |
| 金流對帳 | 比對平台的付款、退款、撥款紀錄和金流方的交易明細，找出差異並分類處理 |
| 賣家結算 | 處理所有已完成、尚未結算的外部賣家子訂單，計算抽成後為每個賣家彙總產生一張撥款單 |
| 撥款執行 | 依撥款單透過金流撥款給賣家，並確認撥款結果 |
| 賣家報表 | 為每個賣家產生銷售報表 |
| 平台報表 | 產生跨賣家的銷售總覽與熱銷排行 |
| 庫存核對 | 以異動紀錄加總核對目前的庫存數字，找出不一致的商品 |
| 折價券到期 | 將已過期且狀態為「可使用」的折價券標記為失效；「已鎖定」的券不處理 |

每日任務的執行順序：

1. 子訂單狀態推進
2. 金流對帳
3. 賣家結算
4. 撥款執行
5. 賣家報表與平台報表

前一步沒有成功，後一步不執行。任務把範圍內的資料都處理過一輪即算成功，個別資料處理失敗不算任務失敗，那些資料留待重試或下一次執行。庫存核對與折價券到期和其他任務沒有相依關係，可獨立執行。

對帳差異的處理：

| 差異類型 | 處理方式 |
|---|---|
| 金流方成功，平台為「處理中」 | 自動依成功處理 |
| 金流方失敗，平台為「處理中」 | 自動依失敗處理 |
| 金流方付款成功，平台為「失敗」且結帳單仍為待付款 | 自動依付款成功處理 |
| 金流方付款成功，平台的結帳單已取消或已有另一筆成功的付款 | 自動全額退款 |
| 金流方有紀錄，平台沒有 | 記為差異，由平台營運人工處理 |
| 平台為成功，金流方沒有紀錄或金額不符 | 記為差異，由平台營運人工處理 |

結帳單有尚未解決的對帳差異時，其子訂單暫不進入結算。

所有批次任務的共通要求：

- 同一個任務在同一時間只會有一個執行個體在跑，即使系統部署了多台機器
- 每次執行留下執行紀錄：任務名稱、處理的資料範圍、起訖時間、成功與失敗筆數、最終結果
- 執行中斷後可從中斷處續跑，不必從頭開始
- 同一個資料範圍重複執行，結果與只執行一次相同
- 單筆資料處理失敗不影響其他筆，失敗的資料記錄原因並可單獨重試
- 任務失敗或逾時未完成時發出告警
- 平台營運可以手動觸發指定資料範圍的重跑
- 每日任務不得影響線上交易的回應時間

### 3.6 稽核與異動追蹤

原則：系統內所有資料異動都要能事後查出是誰、在什麼時間、做了什麼、改了什麼。

依資料的重要程度分三級處理：

| 等級 | 適用資料 | 做法 |
|---|---|---|
| 一 | 金額、庫存、訂單與付款狀態、退款狀態、折價券狀態 | 專屬的異動紀錄（帳本分錄、庫存異動紀錄、狀態變更歷程），只新增不修改 |
| 二 | 商品價格與內容、賣家資料與抽成比例、帳號權限、搶購報名與審核、退款核准與裁決、折價券發放、對帳差異處理、條款版本發布 | 通用稽核紀錄，記下操作者、時間、操作類型、變更前後的值 |
| 三 | 其餘所有資料表 | 基本欄位：建立時間、建立者、最後修改時間、最後修改者、版本號 |

共通規則：

- 稽核紀錄寫在資料庫，並與該次資料異動在同一個資料庫交易內完成，不能只寫在應用程式日誌
- 稽核紀錄只能新增，不能修改或刪除
- 操作者包含會員、賣家帳號、平台營運人員與排程系統，排程系統的異動要記下是哪個批次任務
- 每筆稽核紀錄帶有 trace ID，可以由稽核紀錄查到該次請求的日誌與跨系統鏈路
- 應用程式日誌採結構化格式，用於排查問題，不作為稽核依據
- 日誌與稽核紀錄不得包含密碼、完整卡號等敏感資料；收件人電話與地址等個人資料須遮罩

例外：購物車項目可以直接刪除，其新增、修改、刪除以結構化日誌記錄，不寫入資料庫的稽核紀錄。理由是購物車不涉及金額與庫存（加入購物車不保留庫存，交易從結帳才開始），且變動非常頻繁，留存於資料庫的價值低於其成本。

### 3.7 折價券

只做平台發行的折價券，範圍刻意縮到最小。

券的規格：

- 固定折抵金額，並有最低消費門檻（以結帳單總金額判斷）
- 最低消費門檻必須高於折抵金額，因此使用折價券後的應付金額一定大於零
- 有使用期限，以結帳當下判斷；結帳時鎖定的券即使在付款前過期，該結帳單仍可完成付款並核銷
- 由平台營運直接發放給指定會員，不提供領券頁面
- 每次結帳最多使用一張
- 折扣成本全部由平台吸收，不影響賣家的應收款
- 搶購結帳單不能使用折價券

券的狀態：

| 狀態 | 說明 |
|---|---|
| 可使用 | 已發放給會員，尚未使用且未過期 |
| 已鎖定 | 會員結帳時選用，結帳單尚未付款 |
| 已核銷 | 結帳單付款成功 |
| 已失效 | 超過使用期限 |

狀態流轉：

1. 會員結帳時選用，券由「可使用」變為「已鎖定」
2. 付款成功，券變為「已核銷」
3. 付款失敗時券維持「已鎖定」，因為結帳單仍可重新付款
4. 結帳單取消，券回到「可使用」；若此時已過期則變為「已失效」
5. 已核銷的券不因事後退款而歸還

折扣分攤：

- 折抵金額依各子訂單金額的比例分攤，計算到元為止，無條件捨去
- 捨去後的差額歸給金額最大的子訂單；金額相同時歸給編號最小者
- 各子訂單分攤金額的加總必須等於券的折抵金額
- 子訂單退款時，退給會員的金額為該子訂單金額扣除其分攤的折扣
- 賣家結算以子訂單的原始金額計算，不扣除折扣

### 3.8 付款、退款與撥款

付款：

- 會員對「待付款」的結帳單發起付款，金額為結帳單總金額扣除折價券折抵
- 每次付款嘗試是一筆獨立的付款紀錄

| 付款狀態 | 說明 |
|---|---|
| 處理中 | 已向金流送出請求，尚未得到確定的結果 |
| 成功 | 金流確認收款 |
| 失敗 | 金流確認未收款 |

- 向金流送出請求後若連線逾時或沒有回應，付款維持「處理中」，不可視為失敗
- 結帳單有「處理中」的付款時，不可發起新的付款，避免重複收款
- 付款失敗後，會員可在結帳單逾時前重新付款
- 一張結帳單最多只有一筆成功的付款
- 結帳單已取消後才收到付款成功的結果時，結帳單維持取消，系統自動全額退款。正常流程下處理中的付款會擋住取消，這條規則用來處理金流先回報失敗、之後又更正為成功之類的異常情況

退款的申請與核准：

- 退款以整張子訂單為單位，不做單一商品的部分退款
- 子訂單狀態為已付款、已出貨或已簽收時，會員可申請退款，子訂單進入「退款申請中」
- 「退款申請中」的子訂單不可出貨，也不會被自動完成

| 申請時的子訂單狀態 | 核准方式 |
|---|---|
| 已付款（尚未出貨） | 系統自動核准 |
| 已出貨或已簽收 | 由賣家核准或拒絕；會員對拒絕不服時可申訴，由平台營運裁決 |

- 賣家在 3 天內沒有核准也沒有拒絕時，系統自動核准
- 申請被拒絕時，子訂單回到申請前的狀態，7 天的起算時間仍以出貨或簽收時間為準
- 申請被拒絕後，會員不可對同一張子訂單再次申請，但可在 3 天內向平台提出申訴一次
- 會員提出申訴時，子訂單重新進入「退款申請中」；申訴駁回時，子訂單回到申請前的狀態
- 平台營運裁決申訴：改為核准，或維持拒絕；裁決結果為最終結果
- 從申請到申訴期限結束、或申訴裁決之前，子訂單都不會被自動完成，確保款項不會在爭議未決時進入結算
- 申請核准後，系統向金流發起退款，金額為該子訂單金額扣除其分攤的折扣

| 退款狀態 | 說明 |
|---|---|
| 處理中 | 已向金流送出請求，尚未得到確定的結果 |
| 成功 | 金流確認已退款，子訂單變為「已退款」 |
| 失敗 | 金流確認未退款，系統自動重試；持續失敗時由平台營運處理 |

- 同一筆付款的累計退款金額不得超過原付款金額

退款後的庫存回補：

| 情況 | 回補方式 |
|---|---|
| 退款時尚未出貨 | 退款成功時自動回補 |
| 退款時已出貨或已簽收 | 賣家確認收到退貨後回補；商品無法再販售時賣家可選擇不回補 |

撥款：

- 每次賣家結算為每個外部賣家產生一張撥款單，彙總該次結算的所有子訂單
- 沒有可結算子訂單的賣家不產生撥款單

| 撥款單狀態 | 說明 |
|---|---|
| 待撥款 | 結算完成，尚未向金流送出請求 |
| 處理中 | 已向金流送出請求，尚未得到確定的結果 |
| 成功 | 金流確認已撥款 |
| 失敗 | 金流確認未撥款，下一次撥款執行時重試；持續失敗時由平台營運處理 |

### 3.9 帳本

所有金流事件都以複式記帳記錄。每筆交易的借方與貸方金額相等，分錄只能新增，記錯時以反向分錄更正。

帳本科目：

| 科目 | 意義 |
|---|---|
| 金流存款 | 平台存放在金流方的資金 |
| 代管款項 | 已向會員收取、但子訂單尚未完成的款項，還不屬於任何一方的收入 |
| 應付賣家款項 | 子訂單已完成、尚未撥給外部賣家的款項 |
| 平台營收 | 平台自營商品的銷售收入 |
| 抽成收入 | 向外部賣家收取的抽成 |
| 折價券費用 | 平台吸收的折扣成本 |

各事件的記帳方式：

| 事件 | 記帳方式 |
|---|---|
| 付款成功 | 金流存款與代管款項同時增加，金額為會員實付金額 |
| 子訂單退款成功 | 金流存款與代管款項同時減少，金額為退款金額 |
| 多收的付款被自動退款成功（結帳單已取消，或已有另一筆成功的付款） | 金流存款與代管款項同時減少，金額為該筆付款的金額 |
| 外部賣家的子訂單完成 | 代管款項減少該子訂單的實付金額，折價券費用增加其分攤的折扣，應付賣家款項增加其原始金額 |
| 平台自營的子訂單完成 | 代管款項減少該子訂單的實付金額，折價券費用增加其分攤的折扣，平台營收增加其原始金額 |
| 賣家結算 | 應付賣家款項減少抽成金額，抽成收入增加相同金額 |
| 撥款成功 | 應付賣家款項與金流存款同時減少，金額為撥款金額 |

必須隨時成立的關係：

- 代管款項的餘額，等於所有已付款、尚未完成也尚未退款的子訂單實付金額合計，加上已收款但尚未完成自動退款的金額
- 應付賣家款項的餘額，等於已完成但尚未結算的子訂單原始金額合計，加上尚未撥款成功的撥款單金額合計
- 金流存款的餘額，與金流方的帳戶餘額一致，由金流對帳驗證

### 3.10 金額與價格

- 所有金額以新臺幣計，單位為整數元
- 所有日期的判定（每日任務的處理範圍、報表的日期歸屬、各種「滿 N 天」的計算）以台灣時間（UTC+8）為準
- 一律免運費
- 每個外部賣家有一個抽成比例，由平台營運設定
- 子訂單建立時保存當時的抽成比例，之後調整比例不影響既有訂單
- 抽成金額為子訂單原始金額乘以抽成比例，計算到元為止，無條件捨去
- 撥款金額為子訂單原始金額扣除抽成金額

### 3.11 查詢功能

前端畫面稿完成之前，以本節作為查詢介面的依據；日後設計畫面時再依實際需要調整。

資料新鮮度分為三級：

| 等級 | 意義 |
|---|---|
| 即時 | 查詢者一定看得到自己剛完成的操作結果 |
| 近即時 | 允許短暫延遲，上限寫在各查詢的說明中 |
| 隔日 | 由每日任務產生，反映到前一日為止的資料 |

共通規則：

- 列表類的查詢一律分頁，每頁預設 20 筆，可選擇 20、50、100 筆
- 一律提供頁碼，可跳到指定頁，並回應符合條件的總筆數與總頁數
- 分類瀏覽與關鍵字搜尋最深只能翻到第 1,000 筆
- 其餘列表最深只能翻到第 10,000 筆；符合條件超過 10,000 筆時，總筆數回應「超過 10,000 筆」，提示使用者縮小篩選條件
- 資料量會隨時間持續增長的列表必須限定日期區間，未指定時預設為最近 30 天，單次最長 1 年。適用於：賣家的子訂單列表、庫存異動紀錄、退款申請列表；平台營運依會員或賣家查詢訂單、對帳差異、批次執行紀錄、稽核紀錄、帳本分錄
- 未特別指定排序方式的列表，依時間由新到舊排列
- 賣家只能查到自己的資料，會員只能查到自己的資料
- 近即時的查詢結果僅供顯示，結帳與付款一律以當下的實際資料為準
- 不允許的操作由查詢結果事先排除（例如不列出不能用的折價券），但後端仍須驗證每個請求，不能假設請求一定來自介面

公開查詢（訪客與會員）：

| 查詢 | 內容、篩選與排序 | 新鮮度 |
|---|---|---|
| 分類瀏覽 | 依分類列出上架中的商品；可依價格區間篩選；可依上架時間、價格、銷量排序 | 近即時，60 秒內 |
| 關鍵字搜尋 | 以關鍵字比對商品名稱與描述；篩選與排序同分類瀏覽，另可依相關程度排序 | 近即時，60 秒內 |

| 搶購檔期 | 進行中與即將開始的檔期，及其商品、活動價、每人限購數量與搶購狀態 | 近即時，3 秒內 |
| 熱銷排行 | 銷量最高的商品 | 隔日 |

- 搶購狀態分為「尚未開始」、「搶購中」、「已售完」、「已結束」

- 抽成收入以結算的日期歸屬，折價券費用以子訂單完成的日期歸屬

### 3.12 規則告知

原則：會影響會員或賣家權益的規則，都要在對方做決定之前讓對方知道，並且事後能證明平台已經告知。

條款與同意紀錄：

| 文件 | 對象 | 同意時機 |
|---|---|---|
| 服務條款 | 會員 | 註冊時 |
| 隱私權政策 | 會員 | 註冊時 |
| 賣家條款（含抽成、結算、撥款、退款處理的規則） | 賣家 | 由賣家的管理者帳號代表賣家同意；同意之前，該賣家的所有帳號都無法使用賣家功能 |

- 每份文件都有版本，內容修改時產生新版本，舊版本保留不刪除
- 會員或賣家同意時，記錄同意的對象、文件、版本與時間，此紀錄只能新增不能修改
- 文件發布新版本後，會員或賣家下次登入時須同意新版本才能繼續使用需要身分的功能
- 平台營運可以查詢任一會員或賣家同意過哪些文件的哪些版本

操作時的提醒：

| 對象 | 時機 | 需要告知的規則 |
|---|---|---|
| 會員 | 加入購物車 | 加入購物車不會保留庫存，結帳時才確認是否有貨 |
| 會員 | 結帳確認 | 付款期限與逾時自動取消；一般結帳與搶購結帳各最多一張待付款，主動取消後商品會放回購物車；使用折價券時，退款不歸還券，且退款金額會扣除分攤的折扣 |
| 會員 | 結帳完成 | 付款期限的確切時間 |
| 會員 | 付款處理中 | 付款結果確認中，請勿重複付款 |
| 會員 | 搶購商品頁 | 活動價、每人限購數量、付款期限 10 分鐘、不可使用折價券、退款不退還限購額度 |
| 會員 | 訂單詳情 | 出貨 7 天未確認收貨將自動簽收；簽收 7 天後自動完成，完成後不可申請退款 |

共通規則：

- 提醒中出現的時間長度與數量（30 分鐘、10 分鐘、7 天、3 天、10 件等）必須取自系統實際使用的設定值，不可寫死在文案中，確保告知的內容與系統行為一致
- 有期限的事項以確切的時間點告知（例如「請於 14:30 前完成付款」），由後端在回應中提供
- 現階段只定義需要告知的規則與後端需提供的資料，正式文案於前端階段撰寫

### 3.13 認證與權限

認證：

- 會員、賣家帳號、營運帳號皆以帳號與密碼登入
- 同一帳號連續登入失敗 5 次即鎖定 15 分鐘；登入成功後失敗次數歸零；鎖定與解鎖留下稽核紀錄
- 登入狀態的維持方式見 ADR_009；角色或帳號狀態變更後，最晚在 15 分鐘內生效

授權採角色為基礎的權限控制。一個帳號可以有多個角色；角色與權限的對應固定在系統中，不提供自訂角色。

## 6. 第一版範圍

會員能走完一條完整流程：

1. 賣家上架商品並入庫
2. 訪客或會員瀏覽商品
3. 會員登入後加入購物車
4. 結帳、拆單並預扣庫存
5. 模擬付款，失敗時可重新付款
6. 付款成功後確認扣除庫存，子訂單成為「已付款」
7. 會員可主動取消待付款的結帳單；逾時未付款的結帳單自動取消，兩者都會釋放庫存
8. 處理中的付款由付款結果查詢任務推進到確定的結果

第一版即包含的基礎要求：

- 庫存異動紀錄
- 付款成功的帳本分錄
- 所有資料表的基本稽核欄位
- 日誌與紀錄帶有 trace ID

出貨、簽收、退款、自動完成、結算、撥款、對帳、報表、限時搶購、搜尋引擎留到後續階段。折價券排在結帳、付款、退款、結算都完成之後再加入。

前端排在後端主要功能完成之後，預計分為會員網站、賣家後台、平台營運後台三個部分。
