# ADR_004 資料存取方式

> 狀態：已接受
> 日期：2026-10-14

## 背景

各模組需要存取自己的資料。存取的型態差異很大：

- 一般聚合的讀寫，例如建立結帳單、修改商品
- 熱點上的原子條件更新，例如扣減庫存
- 大量資料的彙總，例如結算、報表、庫存核對

## 考慮過的選項

| 選項 | 優點 | 缺點 |
|---|---|---|
| 全部使用 JPA | 業界最常見；一般讀寫的程式最少 | 原子條件更新與大量彙總仍需寫 SQL；容易在不知不覺中產生 N+1 查詢或過多的查詢 |
| 全部直接寫 SQL | 每條 SQL 都看得見、可控 | 一般讀寫要寫大量重複的對應程式 |
| 以 JPA 為主，效能敏感的操作直接寫 SQL | 兼顧開發效率與可控性 | 要訂清楚使用的時機 |

## 決定

以 JPA 為主，以下情況直接寫 SQL：

| 情況 | 例子 |
|---|---|
| 以單一條件更新完成的原子操作 | 庫存扣減、折價券鎖定 |
| 大量資料的彙總或批次處理 | 結算、報表、庫存核對 |
| 壓測或執行計畫顯示 JPA 產生的查詢有問題時 | 依實際量測結果決定 |

其他規則：

- 實體之間預設延遲載入，需要關聯資料時明確指定一次載入
- 測試中記錄每個請求執行的 SQL 數量，用來發現 N+1 查詢
- 效能敏感的查詢在設計時附上執行計畫

## 後果

- 好處：一般功能開發快；關鍵路徑的 SQL 完全可控，可以直接對照執行計畫調校
- 代價：同一個模組內可能同時有兩種存取方式，需要在程式中清楚區分
- 重新檢討的條件：若 JPA 帶來的問題多到大部分查詢都改寫成 SQL，改為全部直接寫 SQL
