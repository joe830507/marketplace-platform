# ADR_003 PostgreSQL

> 狀態：已接受
> 日期：2026-10-14

## 背景

平台需要關聯式資料庫保存交易、庫存與帳本資料，並支撐高併發的寫入與鎖定。設計上已有幾項需求依賴資料庫的能力：

- 每位會員每種結帳類型最多一張待付款結帳單，以資料庫的唯一性約束保證，而且只對「待付款」的資料生效（《設計_001_領域模型》第 6 節）
- 庫存以原子條件更新扣減，需要清楚可預期的鎖定行為（ADR_008）
- 批次任務與事件發送需要「多台機器不重複處理同一筆資料」的機制

開發者過去主要使用 MySQL。

## 考慮過的選項

| 選項 | 優點 | 缺點 |
|---|---|---|
| MySQL | 開發者熟悉；台灣業界常見 | 不支援部分唯一索引，需要以額外的計算欄位變通；學習收穫較少 |
| PostgreSQL | 直接支援部分唯一索引；資料表結構的變更可以放在交易內，遷移失敗時能整個撤銷；MVCC 與鎖定行為適合做併發實驗；JSON 支援完整 | 開發者需要熟悉新的資料庫與工具 |

兩者都支援 `SELECT ... FOR UPDATE SKIP LOCKED`，可以讓多台機器分工處理批次資料。雲端上兩者都有對應的託管服務。

## 決定

採用 PostgreSQL。平台與模擬金流各使用獨立的資料庫。

## 後果

- 好處：待付款上限可以用一個部分唯一索引完成；可以對照過去的 MySQL 經驗，比較兩者在 MVCC、鎖與隔離級別上的差異
- 代價：需要學習 PostgreSQL 的執行計畫與調校方式
- 重新檢討的條件：無
