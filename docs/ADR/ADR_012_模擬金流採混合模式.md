# ADR_012 模擬金流採混合模式

> 狀態：已接受
> 日期：2026-10-14

## 背景

平台透過獨立的模擬金流服務處理付款。需求與使用者故事已經預設了金流的幾種行為：

- P2：金流重複回報同一筆結果
- P3：連線逾時，付款結果不明，需要主動查詢
- P4：結帳單取消之後才收到付款成功

這些情況只有在金流以非同步方式通知結果時才會發生。模擬金流的介面形式，決定了這些情境能不能被真實地重現與測試。

## 考慮過的選項

| 選項 | 做法 | 評估 |
|---|---|---|
| 純同步 | 平台呼叫金流，回應中直接帶最終結果 | 最簡單，但 P2、P4 不會發生，相關設計無從驗證 |
| 純非同步 | 金流先回應已受理，結果之後以回呼通知 | 真實，但每次付款都要等回呼，測試繁瑣 |
| 混合 | 通常直接回應結果；也可能回應處理中，之後以回呼通知；回呼可能延遲、重複、亂序；平台可主動查詢 | 符合多數真實金流的行為，涵蓋所有已知情境 |

## 決定

採用混合模式：

| 項目 | 做法 |
|---|---|
| 付款請求 | 平台以付款的識別碼作為商家交易編號送出；金流以此辨識重複請求，同一編號只會扣款一次，因此平台可以安全重試 |
| 回應 | 成功、失敗或處理中 |
| 回呼 | 結果確定時，金流呼叫平台的回呼網址；未收到成功回應則依退避間隔重送；可能延遲、重複、亂序 |
| 回呼驗證 | 回呼附上時間戳記與 HMAC-SHA256 簽章，平台驗證簽章、拒絕超過 5 分鐘的時間戳記，並以事件編號去除重複 |
| 主動查詢 | 平台可依商家交易編號查詢交易結果 |
| 平台到金流的驗證 | 平台呼叫金流時帶 API 金鑰 |
| 測試用付款代碼 | 付款請求帶 `tok_success`、`tok_fail`、`tok_async`、`tok_timeout` 等代碼，金流依代碼決定行為，讓自動化測試能精確重現每種情境 |
| 可設定的異常行為 | 延遲、失敗比例、重複回呼比例、回呼延遲，供壓測時模擬不穩定的金流 |

退款、撥款與每日交易明細採用相同的模式，在對應的階段補上。

## 後果

- 好處：P2、P3、P4 都能以自動化測試重現；平台必須正確處理逾時、重試、重複與亂序，這些正是分散式系統的核心問題；回呼簽章讓平台的安全設計有具體的實作
- 代價：模擬金流本身成為一個需要開發與測試的服務
- 重新檢討的條件：日後串接真實金流時，以付款模組的轉接層對應真實金流的介面，平台其他部分不受影響（《設計_001_領域模型》第 5 節）
