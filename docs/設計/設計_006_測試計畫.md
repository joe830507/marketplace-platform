> 狀態：定版
> 版本：1.0
> 最後更新：2026-10-14
> 依據：《需求_001_需求規格》1.7、《需求_002_使用者故事》1.5、《設計_002_狀態圖與循序圖》1.0、《設計_004_資料庫設計》1.1、《設計_005_API規格》1.0、ADR_001、ADR_005、ADR_007、ADR_012

## 1. 目的與範圍

- 定義測試的層級、各層測什麼、用什麼工具
- 把使用者故事的驗收條件對應到具體的測試
- 定義一個功能「完成」的標準

第 5 節的對應表只涵蓋第一版範圍內的使用者故事；其他故事在各自的階段補上。壓測另寫《壓測計畫》，在併發正確性階段開始前撰寫。

## 2. 測試的層級

採用測試金字塔：越下層數量越多、執行越快；越上層數量越少、越接近真實使用。

| 層級 | 測什麼 | 範圍 | 外部依賴 | 數量 |
|---|---|---|---|---|
| 單元測試 | 純業務邏輯：狀態轉換規則、金額計算、折扣分攤的尾數、冪等雜湊、期限計算 | 單一類別 | 無，不啟動 Spring | 最多 |
| 模組測試 | 單一模組的完整行為：資料存取、SQL、資料庫限制、交易、發布的事件 | 單一模組 | 真的 PostgreSQL；其他模組以替身取代 | 多 |
| API 測試 | 驗收條件：透過 HTTP 呼叫 API，驗證回應、資料庫狀態與事件 | 整個主應用程式 | 真的 PostgreSQL；模擬金流以 HTTP 替身取代 | 中 |
| 併發測試 | 同時發生的請求下，資料庫限制與原子操作是否守得住 | 整個主應用程式或單一模組 | 真的 PostgreSQL | 少，但不可省略 |
| 端對端測試 | 主應用程式與真的模擬金流一起運作 | 兩個服務 | Docker Compose | 最少 |
| 架構測試 | 模組邊界、程式慣例 | 整個程式碼 | 無 | 少 |

### 2.1 為什麼模組測試與 API 測試都用真的 PostgreSQL

我們有多條規則由資料庫保證：部分唯一索引（待付款上限、處理中付款上限）、`CHECK` 限制（庫存不為負）、原子條件更新、唯一性約束提供的冪等。記憶體資料庫無法忠實重現這些行為，以它測試等於沒測。

### 2.2 為什麼 API 測試用模擬金流的替身

API 測試需要精確控制金流的每一種回應，包括延遲、逾時、錯誤格式，且必須快速、穩定。以 HTTP 替身（例如 WireMock）在測試中直接設定回應。

模擬金流本身的行為，以及兩個服務之間的實際串接，由端對端測試驗證。

## 4. 共通做法

### 4.1 時間

- 程式一律透過注入的時鐘取得時間（《設計_003_系統架構》第 6 節）
- 測試使用可以手動前進的時鐘，例如「前進 31 分鐘後執行逾時取消任務」，不使用真實的等待
- 架構測試禁止在業務程式中直接呼叫 `Instant.now()`、`LocalDateTime.now()` 等方法

### 4.2 測試資料

- 每個測試自己建立需要的資料，使用新產生的識別碼，不依賴其他測試留下的資料，也不依賴執行順序
- 以建構器建立測試資料，例如「一個有 10 件庫存的上架商品」，只寫出與該測試有關的欄位
- 整個測試執行期間共用一個 PostgreSQL 容器，以縮短時間；因為每個測試的資料互不重疊，不需要在測試之間清空資料庫
- 需要統計全域數量的測試（例如批次任務），以自己建立的資料範圍為條件查詢，不計算全表
- 查詢類的測試（例如搜尋、排序、分頁）以自己建立的分類或獨特的關鍵字限定範圍，否則結果會混入其他測試建立的商品
- 會前進時鐘或執行批次任務的測試，不與其他測試平行執行，並在結束時將時鐘還原。例如前進 31 分鐘後執行逾時取消任務，會連帶取消其他測試尚未付款的結帳單

### 4.3 命名與可追溯性

- 測試類別以被測對象命名，例如 `CheckoutApiTest`、`StockReservationModuleTest`
- 每個對應驗收條件的測試，以 `@DisplayName` 寫出故事編號與情境，例如 `O3 同時送出：只有一個請求建立結帳單`
- 從測試報告就能看出每個故事的每個情境是否通過

### 4.4 驗證的內容

API 測試除了 HTTP 回應，還要驗證：

| 項目 | 例子 |
|---|---|
| 資料庫狀態 | 庫存數字、結帳單狀態 |
| 異動與稽核紀錄 | 有對應的庫存異動紀錄、狀態歷程 |
| 發布的事件 | 發布了「結帳單已建立」事件 |
| 不該發生的事 | 失敗時沒有建立任何結帳單、沒有預扣庫存 |

最後一項特別重要：多數錯誤不是「沒做該做的事」，而是「做了不該做的事」。

## 6. 特殊的測試

### 6.1 併發測試

做法：同時啟動多個執行緒，以同一時間點放行，對同一筆資料送出請求，結束後驗證結果。

第一版必須有的併發測試：

| 測試 | 驗證 |
|---|---|
| 同一冪等鍵同時結帳 | 只有一張結帳單 |
| 同一會員同時送出兩筆不同的結帳 | 只有一筆成功，另一筆為 `PENDING_CHECKOUT_EXISTS` |
| 多人同時購買庫存只剩少量的商品 | 成功的數量不超過庫存；庫存不為負；異動紀錄加總與庫存數字一致 |
| 兩筆結帳以相反順序包含相同的兩項商品 | 不會死鎖（《設計_004_資料庫設計》12.2） |
| 同一結帳單同時發起付款 | 只有一筆處理中的付款 |
| 同一金流事件同時送達 | 付款狀態只更新一次，分錄只有一筆 |
| 逾時取消與付款成功同時發生 | 結果只會是「已付款」或「已取消並自動退款」其中之一，不會兩者都成立 |

併發測試的結果可能因執行時機而不同，每個測試重複執行 20 次，任何一次失敗都視為失敗。

### 6.2 模組邊界與程式慣例

| 檢查 | 工具 |
|---|---|
| 模組之間沒有違規依賴與循環依賴 | Spring Modulith |
| 業務程式不直接取得系統時間 | ArchUnit |
| 業務程式不使用 `float`、`double` 型別，避免金額與比例出現小數誤差 | ArchUnit |
| 模組不存取其他模組的 `internal` 套件 | Spring Modulith |

### 6.3 Outbox 機制

驗證 ADR_007 要求的行為，而不只是相信函式庫：

| 測試 | 驗證 |
|---|---|
| 訂閱者處理失敗 | 事件維持未完成，之後被重新發送並成功處理 |
| 多個訂閱者其中一個失敗 | 只有失敗的訂閱者收到重送；成功的訂閱者不會重複收到 |
| 同一事件送達兩次 | 訂閱者只處理一次 |
| 業務交易撤銷 | 事件不會被發送 |
| 應用程式重啟 | 重啟前未完成的事件，重啟後會被發送 |

為了測試「付款已成功但訂單尚未更新」這類情境，測試中需要能暫停事件的發送，在指定時機再放行。

### 6.4 模擬金流的情境

API 測試以 HTTP 替身重現，端對端測試以真的模擬金流與付款代碼重現：

| 情境 | API 測試的替身設定 | 端對端測試的付款代碼 |
|---|---|---|
| 成功 | 回應成功 | `tok_success` |
| 失敗 | 回應失敗 | `tok_fail` |
| 非同步成功 | 回應處理中，之後由測試送出回呼 | `tok_async` |
| 逾時 | 回應延遲超過平台的逾時設定 | `tok_timeout` |
| 回呼簽章錯誤 | 由測試送出簽章錯誤的回呼 | 不適用 |
| 回呼時間戳記過期 | 由測試送出 6 分鐘前的回呼 | 不適用 |
| 重複回呼 | 由測試送出相同事件編號兩次 | 開啟重複回呼的異常行為設定 |
| 連線失敗 | 第一次連線失敗、第二次回應成功 | 不適用 |

### 6.5 端對端測試

只涵蓋最關鍵的路徑，每條都同時經過兩個服務：

1. 註冊、登入、加入購物車、結帳、以 `tok_success` 付款，結帳單變為已付款
2. 以 `tok_timeout` 付款，付款先為處理中，之後經由回呼變為成功
3. 以 `tok_async` 付款後讓結帳單逾時，回呼到達時觸發自動退款的要求

端對端測試需要先把兩個服務建置成容器映像檔，再以 Docker Compose 啟動。

### 6.6 模擬金流本身的測試

模擬金流是獨立的服務，有自己的單元與 API 測試：每個付款代碼的行為、以商家交易編號去除重複請求、回呼的簽章與重送、異常行為設定。

## 7. 覆蓋率

- 以 JaCoCo 產生報告，不設定讓建置失敗的強制門檻
- 核心模組（訂單、庫存、付款、帳本）的分支覆蓋率目標為 80%
- 由規格檔產生的程式不計入

覆蓋率只能看出哪些程式沒被執行過，無法看出測試是否驗證了正確的事。第 5 節的對應表才是判斷測試是否足夠的主要依據。

## 8. 完成的定義

一個功能符合以下全部條件才算完成：

1. 第 5 節對應表中該功能的所有情境都有測試且通過
2. `./mvnw verify` 全部通過，包含所有層級的測試、模組邊界驗證與程式格式檢查
3. API 有變動時，OpenAPI 規格檔已先更新，且 API 測試以規格檔驗證通過；新增的錯誤代碼已加入《設計_005_API規格》2.4
4. 資料表有變動時，《設計_004_資料庫設計》與 Flyway 遷移腳本已同步更新
5. 做了新的架構決策時，已寫成 ADR
6. 新增的批次任務、事件、狀態轉換，已在相關設計文件中補充

## 9. 執行方式

| 指令 | 執行的測試 | 時機 |
|---|---|---|
| `./mvnw test` | 單元、模組、架構測試 | 開發時頻繁執行 |
| `./mvnw verify` | 全部，包含 API、併發測試與程式格式檢查 | 提交程式之前 |
| `./mvnw verify -Pe2e` | 端對端測試；會建置映像檔並啟動 Docker Compose | 合併到主要分支之前 |

日後建立持續整合時，每次推送程式都執行 `./mvnw verify`。
